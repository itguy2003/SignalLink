SignalLink Green — .NET Core 백엔드 (**기준 백엔드**, 전체 기능)
====================================================================

무엇인가
--------
이 프로젝트가 **기준 백엔드**다 — 스키마(EF Core 마이그레이션)와 부트스트랩
(최상위 기관·admin)을 이쪽이 맡는다. FastAPI(../backend)는 **같은 DB·같은
토큰·같은 응답 모양** 위의 병행 구현으로 함께 뜬다.

  FastAPI  : http://127.0.0.1:8015
  .NET     : http://127.0.0.1:8016

실행
----
  cd backend-dotnet
  dotnet run          # ../backend/.env 와 ../backend/signallink.db 를 그대로 쓴다

프런트를 이쪽에 붙이려면:
  VITE_API_PROXY=http://127.0.0.1:8016 npm run dev

계약을 맞추는 것들
------------------
1. 같은 DB — DATABASE_URL 이 비면 ../backend/signallink.db, postgresql:// 이면 Npgsql.
   **스키마의 주인은 이쪽의 EF 마이그레이션**(Migrations/) — 아래 "스키마
   소유권" 절 참조. Alembic 은 d491ad229086 에서 동결(../backend/alembic/FROZEN.txt).
2. 같은 토큰 — .env 의 SECRET_KEY 로 HS256. 두 서버가 서로 발급한 토큰을 받는다.
   (256비트 미만 키는 HMAC 0 패딩으로 서명 동일성을 유지 — Services/Security.cs)
3. 같은 장치 채널 — .env 의 DEVICE_MASTER_KEY 로 HKDF-SHA256 + AES-256-GCM.
   FastAPI 의 crypto 모듈로 만든 봉투가 .NET WS 채널에서 그대로 열린다(검증 완료).
4. 같은 응답 모양 — snake_case JSON, 같은 오류 문구, 같은 페이지 형식.

스키마 소유권 (2026-09-07 Alembic → EF Core 이관)
--------------------------------------------------
  - 첫 마이그레이션 20260907025044_InitialCreate 는 Alembic 최종 시점
    (d491ad229086)의 스키마와 동일하다 — 인덱스·유니크 이름까지 Alembic 의
    것을 그대로 썼다(AppDbContext.ApplySchemaRules). 이름을 맞춘 이유:
    베이스라인된 옛 DB 와 EF 가 새로 만든 DB 에서 이후 마이그레이션이
    같은 이름을 참조해야 하기 때문.
  - 기동 순서(Services/DbStartup.cs): ① Alembic 시절 DB 면 InitialCreate 를
    "적용됨"으로만 기록(베이스라인, 데이터 보존) ② 밀린 마이그레이션 적용
    ③ 부트스트랩(최상위 기관 + admin, FastAPI init_db 와 같은 규칙).
  - 스키마 변경 절차: AppDbContext 모델 수정 → `dotnet ef migrations add <이름>`
    → **dotnet build** (마이그레이션은 빌드해야 DLL 에 실린다) → 서버 기동 시
    자동 적용 → FastAPI 의 app/models/* 거울도 함께 수정.
  - 알려진 표현 차이(무해): Alembic 은 uq_* 를 테이블 UNIQUE 제약으로,
    EF 는 이름 있는 유니크 인덱스로 만든다. 보장(컬럼 조합)은 동일함을
    schema_diff 로 확인했다. 단, 옛 DB 에서 uq_* 를 이름으로 지우는
    마이그레이션은 실패할 수 있다 — 그때는 테이블 재작성으로 처리할 것.
  - 마이그레이션은 SQLite 공급자로 생성됐다. 운영 PostgreSQL 최초 구축 전에
    DATABASE_URL 을 놓고 `dotnet ef database update` 로 리허설할 것.
  - dotnet-ef 는 로컬 도구다(dotnet-tools.json): `dotnet tool restore` 후 사용.
  - **새 테이블을 추가했으면 .NET 을 먼저 기동할 것.** FastAPI 를 먼저 띄우면
    create_all(개발 편의)이 새 테이블을 자기 DDL 로 선점해, 뒤에 도는 EF
    마이그레이션이 "table already exists" 로 충돌한다. (열 추가는 create_all
    이 건드리지 않아 무관하다.)
  - 기동 시 EF 10 의 PendingModelChangesWarning 은 억제되어 있다(Program.cs) —
    동적 모델 구성(ApplySchemaRules)과의 거짓 양성. 진짜 비교는
    `dotnet ef migrations has-pending-model-changes` 로 한다.

남은 차이 (의도된 것)
---------------------
  - 부트스트랩(최상위 기관·admin 생성)은 이제 양쪽 다 멱등으로 수행한다 —
    어느 쪽을 먼저 띄워도 같은 결과다(.NET DbStartup / FastAPI init_db).
  - 날씨·명화 데이터는 FastAPI 와 같은 자리표시자다(원본도 TODO).
  - WS 허브는 프로세스 로컬 — 두 서버를 동시에 띄우면 장치는 접속한 쪽에서만
    푸시를 받는다(다른 쪽 변경도 하트비트 버전 비교로 따라잡는다).
  - FastAPI 의 pytest 스위트는 파이썬 전용이라 .NET 을 직접 검증하지 않는다.
    대신 **../backend-dotnet.Tests** (xUnit)가 .NET 을 검증한다:
      cd backend-dotnet.Tests && dotnet test
    단위(암호 해시·HMAC 패딩·JWT 클레임·장치 채널 봉투·합성 버전 산식·
    CSV/병합·공유 판정) + 통합(진짜 서버를 임시 SQLite 로 부팅해 부트스트랩·
    인증·공유 흐름·스케줄 검증·장치 고유번호 형식). 대조 스크립트
    (scratchpad/compare.py·write_verify.py)의 두-서버 실측은 별도로 유효하다.

[2026-09-18] 스케줄의 소속기관 공지 '참조' (마이그레이션 ScheduleItemNoticeRef)
- schedule_item.org_notice_id (FK org_notice, ON DELETE SET NULL). 참조가 있으면
  content_id/인라인은 버린다(정본 하나). 검증: 스케줄 기관의 자기/상위기관

  남는 아이템이 없으면 데모.

- 플레이어 규약: 시간지정에서 같은 요일·시간대에 여러 장이 맞으면

  동일 규칙 필요).
- 편집기: 공지 탭 카드/[소속기관 공지 추가] 모두 참조 한 줄로 담는다.

[2026-09-18] 소속기관 공지 사용기간에 시각 포함 (마이그레이션 OrgNoticePeriodTime)
- 저장 형식: "YYYY-MM-DDTHH:MM" (org_notice.start/end_date, str16). 날짜만
  보내오면 시작은 T00:00, 종료는 T23:59 로 넓혀 저장한다. 형식 오류 문구:
  "기간은 YYYY-MM-DD 또는 YYYY-MM-DDTHH:MM 형식이어야 합니다."
- 판정(notice_active_on/NoticeActiveOn): 분 단위 문자열 비교, 경계 포함,
  **서버 로컬 시각** 기준(관리자가 화면에서 고른 시각 그대로). 날짜만 저장된
  옛 값은 읽을 때도 같은 규칙으로 넓힌다.
- SQLite 는 TEXT 라 이 마이그레이션은 빈 연산이다(스냅샷 일치용). 프런트
  입력은 datetime-local, 표시는 T 를 공백으로 푼다.
